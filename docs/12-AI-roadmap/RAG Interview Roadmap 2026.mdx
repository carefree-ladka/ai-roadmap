## Phase 1 — RAG Fundamentals

Must know before anything else.

### Learn

| Topic | What the interviewer expects |
|---|---|
| What is RAG? | LLM retrieves external knowledge before generating an answer. |
| Why RAG? | Reduce hallucinations, use private/company data, avoid retraining. |
| RAG vs Fine-tuning | Knowledge retrieval vs updating model weights. |
| RAG vs Long Context 🆕 | When a bigger context window replaces retrieval, and when it doesn't (cost, freshness, precision, citations). |
| Basic Pipeline | Documents → Chunk → Embed → Vector DB → Retriever → LLM → Answer. |

### Interview Questions
- Explain RAG in 2 minutes.
- Why not just fine-tune instead of using RAG?
- Where do embeddings fit in the pipeline?
- If context windows keep growing, why do we still need RAG? 🆕

### Build
A simple PDF chatbot using **FastAPI + Ollama + ChromaDB**.

## Phase 2 — Embeddings & Vector Databases

Asked almost everywhere.

### Embeddings

| Topic | Notes |
|---|---|
| Embedding models | `nomic-embed-text`, BGE, E5, OpenAI `text-embedding-3`, Gemini. |
| Dimensions | 768, 1024, 1536, etc. — trade-off between accuracy and storage/speed. |
| Cosine similarity | Most common similarity metric for semantic search. |
| Dot product | Sensitive to vector magnitude; equivalent to cosine if vectors are normalized. |
| Normalization | Why you normalize vectors before comparing. |
| Matryoshka embeddings 🆕 | Truncatable embeddings (e.g., OpenAI v3, Nomic) that let you shrink dimensions for speed without re-embedding. |

### Vector Databases

| Database | Why use it |
|---|---|
| Chroma | Local development, prototyping. |
| Pinecone | Managed, production-grade, serverless. |
| Qdrant | Fast, open-source, filtering support. |
| Weaviate | Hybrid search built in. |
| Milvus | Large-scale retrieval, billions of vectors. |
| pgvector 🆕 | Postgres extension — good when you already run Postgres and want one system of record. |

### Indexing Internals 🆕 (frequently skipped, but senior interviewers love it)
- **HNSW** (Hierarchical Navigable Small World) — graph-based ANN index, most common default.
- **IVF / IVF-PQ** — cluster-based index used by FAISS for very large datasets.
- **Exact vs Approximate Nearest Neighbor (ANN)** — why approximate search is used at scale, and the recall/speed trade-off.
- **Quantization** (scalar/product quantization) — reducing vector memory footprint in production.

### Interview Questions
- Why cosine similarity over Euclidean distance?
- How does approximate nearest neighbor search work (HNSW basics)?
- Difference between FAISS and Chroma?
- How would you shard/scale a vector index to 100M+ vectors? 🆕

### Build
Store PDFs in Chroma; benchmark Chroma vs Qdrant on the same dataset.

## Phase 3 — Chunking Strategies (Very Frequently Asked)

### Chunking Methods

| Method | Use Case |
|---|---|
| Fixed-size chunking | Simple, fast baseline. |
| Recursive chunking | LangChain default — splits by structure first, then size. |
| Semantic chunking | Splits based on meaning/embedding similarity shifts. |
| Sentence chunking | Good for precise QA systems. |
| Markdown/HTML chunking | Preserves headers and document structure. |
| Code chunking | AST-aware splitting for GitHub/code assistants. |
| Sliding window / late chunking 🆕 | Embed the full doc first, then chunk — preserves more context per chunk (used in newer embedding-aware pipelines). |

### Understand
- Chunk overlap and why it matters.
- Chunk size trade-offs (recall vs precision vs token cost).
- Token counting (tiktoken or model-specific tokenizers).
- Metadata attached to chunks (source, page, section, timestamp).

### Interview Questions
- What's the best chunk size, and how do you decide?
- Why use overlap between chunks?
- Why does semantic chunking improve retrieval quality?
- How do you chunk structured data like tables or code? 🆕

### Build
Compare chunk sizes: **256 / 512 / 1024** tokens and measure retrieval quality differences.

## Phase 4 — Retrieval Techniques (Highest Priority)

### Retrieval Types

| Technique | Why |
|---|---|
| Similarity search | Default vector retrieval. |
| MMR (Maximal Marginal Relevance) | Adds diversity to retrieved chunks. |
| BM25 | Classic keyword/sparse retrieval. |
| Hybrid search | Combines vector + keyword for best recall. |
| Metadata filtering | Department/date/user/tenant filters. |
| Top-K retrieval | Choosing how many chunks to retrieve. |
| Query rewriting / HyDE 🆕 | Rewrite or hypothetically-answer the query before embedding it, to improve match quality. |
| Small-to-big / Parent-child retrieval 🆕 | Retrieve small precise chunks, return the larger parent for context (see Phase 7). |

### Retriever Settings
- `k` (number of results)
- score threshold
- search type (`similarity`, `mmr`, `similarity_score_threshold`)
- metadata filters

### Interview Questions
- Difference between similarity search and MMR?
- How does hybrid search improve recall over pure vector search?
- What is metadata filtering and when would you use it?
- What is HyDE and when does it help? 🆕

### Build
FastAPI endpoint with a configurable retriever:

```python
from langchain_chroma import Chroma

retriever = db.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 5, "fetch_k": 20}
)
```

### Learn

| Concept | Notes |
|---|---|
| Hybrid retrieval | BM25 + vector search combined. |

## Phase 7 — Advanced RAG Patterns

Appear frequently in senior interviews.

### 1. Multi-Query RAG
Generate multiple search queries from one user question to improve recall.
> Example: "Explain React Context" → "React Context API", "Context Provider pattern", "state sharing in React".

### 2. Parent Document Retriever
Retrieve small chunks for precision, return the larger parent document for full context. Useful for documentation.

### 3. Contextual Compression
Compress retrieved chunks before sending to the LLM to reduce token usage and noise.

### 4. Self-RAG
The LLM decides dynamically: retrieve? generate directly? retrieve again if the first pass was insufficient?

### 5. GraphRAG
Knowledge-graph-based retrieval using entities and relationships (e.g., Neo4j). Good for multi-hop reasoning questions.

### 6. Agentic RAG
Combines tools, memory, retrieval, and a planner — typically built with LangGraph.

### 7. Contextual Retrieval 🆕
Anthropic's technique of prepending short LLM-generated context to each chunk *before* embedding, so chunks retain document-level meaning even in isolation — improves retrieval accuracy significantly on long documents.

### 8. Corrective RAG (CRAG) 🆕
A lightweight evaluator grades retrieved docs; if relevance is low, the system falls back to web search or query reformulation instead of generating from bad context.

### Interview Questions
- When would you use GraphRAG instead of vector RAG?
- What problem does Self-RAG solve?
- How is Contextual Retrieval different from adding more chunk overlap? 🆕

## Phase 8 — RAG Evaluation (Very Popular in 2026)

### Retrieval Metrics

| Metric | Meaning |
|---|---|
| Recall@K | Were relevant docs retrieved? |
| Precision@K | Were retrieved docs actually relevant? |
| MRR | Ranking quality (position of first relevant result). |
| NDCG | Ranking usefulness, weighted by position. |

### Generation Metrics

| Metric | Meaning |
|---|---|
| Faithfulness | Is the answer grounded in the retrieved context? |
| Answer Relevance | Does the answer address the user's question? |
| Context Relevance | Was the retrieved context actually useful? |
| Groundedness | Absence of hallucination. |

### Frameworks
- **Ragas** — automated RAG evaluation metrics.
- **LangSmith** — tracing, dataset evals, regression testing.
- **DeepEval** — pytest-style LLM evaluation.
- **TruLens** 🆕 — feedback functions for groundedness/relevance tracking.

### Interview Questions
- How do you evaluate RAG quality end-to-end?
- How do you detect and reduce hallucinations?
- How would you set up a regression test suite for a RAG pipeline? 🆕

## Phase 9 — Production RAG Architecture (Senior Round)

### Full Architecture

| Layer | What to know |
|---|---|
| API | FastAPI async endpoints, streaming responses. |
| Ingestion | PDF/DOCX/PPTX parsing (`unstructured`, `PyMuPDF`, OCR for scans). |
| Queue | Background/async ingestion (Celery, RQ, or async workers). |
| Storage | S3 (raw files) + Postgres (metadata). |
| Vector DB | Chroma/Qdrant/pgvector. |
| Cache | Redis (embedding cache, response cache). |
| LLM | Ollama (local) / OpenAI / Gemini (fallback/production). |
| Observability | LangSmith traces, structured logging, request tracing. |

### Production Concepts
- Async ingestion pipelines
- Embedding cache (avoid re-embedding unchanged docs)
- Token streaming to the client
- Conversation memory (short-term + long-term)
- Access control / multi-tenant document isolation
- Metadata filtering per user/tenant
- Rate limiting
- Retry logic and fallback models
- Cost tracking per request 🆕

### Interview Questions
- How would you scale RAG to 1 million+ documents?
- How do you reduce latency in a RAG pipeline?
- How do you reduce embedding and LLM cost at scale?
- How do you isolate documents between tenants in a multi-tenant RAG system? 🆕

## Phase 10 — Security, Guardrails & Failure Modes 🆕

Increasingly asked once interviewers know you can build the happy path.

### Learn

| Topic | Why it matters |
|---|---|
| Prompt injection | Malicious content inside retrieved documents trying to hijack the LLM's instructions. |
| Data leakage / access control | Preventing a user from retrieving another tenant's private chunks. |
| PII redaction | Scrubbing sensitive data before embedding or logging. |
| Guardrails | Input/output validation (e.g., NeMo Guardrails, Guardrails AI, simple regex/LLM-based filters). |
| Citation grounding | Forcing the model to only answer from retrieved sources and cite them. |
| Graceful degradation | What happens when retrieval returns nothing relevant — refuse vs fallback vs say "I don't know." |

### Interview Questions
- How do you defend a RAG system against prompt injection from a malicious document?
- How do you enforce per-tenant document isolation in the vector store?
- How do you make the LLM say "I don't know" instead of hallucinating when retrieval fails?

## Quick-Reference Cheat Sheet 🆕

**One-line answers for whiteboard/verbal rounds:**

- **RAG** = Retrieve relevant context, then generate an answer grounded in it.
- **Cosine similarity** = measures angle between vectors, ignores magnitude — best for semantic similarity.
- **Chunking** = balance recall (smaller chunks) vs context completeness (larger chunks); overlap prevents boundary information loss.
- **MMR** = trades a little relevance for diversity, avoiding near-duplicate chunks.
- **Hybrid search** = BM25 catches exact keyword/terminology matches; vector search catches semantic meaning — combine with RRF.
- **Reranker** = a cross-encoder that looks at query+doc together for a more accurate (but slower) relevance score than a bi-encoder.
- **LCEL** = declarative, composable chains using the `|` operator; supports native streaming and async.
- **Self-RAG / CRAG** = the system evaluates its own retrieval quality before generating, instead of blindly trusting top-K results.
- **GraphRAG** = better for multi-hop, relationship-heavy questions; vector RAG is better for single-fact lookup.
- **Production RAG** = ingestion queue + embedding cache + vector DB + Redis cache + observability + guardrails, not just "LLM + vector DB."
