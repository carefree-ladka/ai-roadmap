## 4. FastAPI for Production

**API:** async endpoints, dependency injection, Pydantic validation, middleware, exception handling, API versioning.
**Performance:** connection pooling, async DB, Redis caching, streaming responses, background jobs, concurrency.
**Reliability:** timeout, retry, circuit breaker, fallback, rate limit.

```
User → FastAPI → LLM → timeout?
                        ├── no  → response
                        └── yes → retry → fallback model
```

## 5. LLM Serving

**Development:**
```
FastAPI → Ollama → Llama
```
**Production:**
```
FastAPI → LLM Service → vLLM / TGI / Managed Model API → GPU
```
Learn: Ollama, vLLM, GPU inference, CPU vs GPU, model loading, quantization, batching, continuous batching, concurrent requests, tokens/sec, time to first token (TTFT), throughput.

**Critical interview distinction:** **Latency** = how long one request takes. **Throughput** = how many requests you can process over time. Optimizing for one can hurt the other (e.g., large batch sizes raise throughput but can raise per-request latency).

## 6. Streaming

```
User → FastAPI → LLM → token → token → token → token → React
```
Learn: `StreamingResponse`, SSE, WebSockets, async generators, token streaming, connection handling. For a ChatGPT-style clone, **SSE + FastAPI** is the pragmatic default (simpler than WebSockets when you only need server→client push).

## 13. Reliability Patterns

**Timeout:**
```
LLM doesn't respond → timeout → return fallback
```
**Retry:** only retry appropriate (transient) failures — never blindly retry a failure caused by bad input.

**Circuit Breaker:**
```
LLM failing repeatedly → Circuit OPEN → Don't keep calling LLM
```
**Fallback:**
```
Primary model → failure → Smaller/secondary model
```

---

## 14. Security

Beyond normal API security: authentication, authorization, API keys, JWT, secrets management, prompt injection, indirect prompt injection, PII protection, data isolation, tool permissions, MCP security, RAG access control, rate limiting, audit logging.

```
User → Permission check → Agent → Tool → Authorization check → External system
```
**Golden rule:** never rely only on the LLM to enforce permissions — the model is not a security boundary; every privileged action needs a deterministic authorization check outside the model's control.

Already covered in depth in the LangSmith guide — in production, track: latency, errors, tokens, cost, model, prompt version, retrieval quality, tool calls, agent steps, failed requests, user feedback, across the full chain:


## 16. Evaluation in CI/CD

Don't wait until production to find quality regressions:
```
Code change → Run tests → Run LLM evaluation → RAG evaluation → Safety tests → Deploy
```
```
Faithfulness < 0.85 → FAIL → Don't deploy
```
This is where the Evaluation guide's golden dataset + regression testing becomes an actual deployment gate, not just a report.

## 17. Model & Prompt Versioning

Treat prompts/models like code — track model, prompt, retriever, embedding model, chunking strategy, reranker together as one versioned "configuration," so a quality drop can be traced to exactly what changed.

## 20. Kubernetes for AI Workloads

**Missing from the original — "good to know" in the roadmap but frequently probed one level deeper in senior interviews.**
- **Deployments** manage your stateless FastAPI/agent pods; **StatefulSets** for anything needing stable identity/storage (rare for the API layer, common for some vector DBs).
- **Services + Ingress** route external traffic to pods; the Ingress is typically where TLS termination and path-based routing to different model/agent endpoints happen.
- **HorizontalPodAutoscaler (HPA)** scales FastAPI replicas on CPU/request-rate; GPU-bound LLM-serving pods often need **custom metrics** (e.g., queue depth, GPU utilization) rather than plain CPU, since a GPU pod can look "idle" on CPU while fully saturated on GPU.
- **Node pools / taints & tolerations** to schedule GPU-heavy inference pods only onto GPU nodes, keeping cheap CPU-only work off expensive GPU nodes.
- **Resource requests/limits** matter more than typical services — under-provisioning a model-serving pod causes OOM kills mid-generation, which is a worse failure mode than a slow response.

**Interview point:** the key nuance to state explicitly is that **autoscaling an LLM-serving pod on CPU alone is usually wrong** — you need GPU-utilization or request-queue-depth-based scaling instead.

## 21. Deployment Strategies

**Missing from the original — listed as "good to know" but commonly asked to be explained, not just named.**

- **Blue-Green** — run two full production environments ("blue" = current, "green" = new); switch traffic all at once by flipping a router/load-balancer target. Fast rollback (just flip back), but doubles infrastructure cost during the switch window.
- **Canary** — route a small % of traffic (e.g., 5%) to the new version, monitor quality/latency/error metrics, then progressively increase. Lower blast radius than blue-green, but needs good automated metrics to decide "promote vs rollback" — this is where the evaluation + observability stack from earlier guides directly plugs in.
- **Feature flags** — gate a new prompt, model, or agent behavior behind a flag so it can be enabled for specific users/cohorts and killed instantly without a redeploy. Especially useful for LLM apps because "bad output quality" often isn't caught by infra health checks — you need a fast kill-switch independent of your deploy pipeline.

**Interview point:** for LLM/agent changes specifically, canary + feature flags are preferred over pure blue-green, because quality regressions (not just crashes) are the main risk, and canary lets you catch a quality dip on 5% of traffic before it hits everyone.

## 22. Cost Optimization

Reduce:
```
Token cost:      huge prompt → context compression → smaller prompt
Model cost:      simple task → small model, complex task → large model
Retrieval cost:  retrieve 50 → rerank → send top 5 to LLM
```
Also: caching, batching, quantization, smaller models, prompt optimization, embedding caching, **model routing** (send easy queries to a cheap/fast model, hard ones to a strong model — a classifier or even the model itself can make this routing decision).

## 23. GPU & Inference Optimization Deep Dive

**Missing from the original — "good to know" listed but under-explained; worth one level deeper.**
- **Quantization** — reduce model weight precision (FP16 → INT8 → INT4) to cut memory footprint and speed up inference, trading a small amount of quality for large efficiency gains. Know that lower-bit quantization has diminishing-returns quality loss and isn't free.
- **Continuous batching** (vs static batching) — dynamically add new requests into an in-flight batch as others finish, instead of waiting for a full batch to form; this is what makes serving frameworks like vLLM dramatically more throughput-efficient than naive batching.
- **KV-cache management** — the attention key/value cache grows with context length and concurrent requests; it's usually the actual memory bottleneck on a GPU, not the model weights themselves. vLLM's "PagedAttention" is specifically designed to manage this efficiently.
- **Time-to-first-token (TTFT) vs total generation time** — for a streaming chat UI, TTFT matters more for perceived responsiveness than total completion time; some optimizations (e.g., speculative decoding) specifically target reducing TTFT/inter-token latency.

## 24. Load Testing for LLM Applications

**Missing from the original.** LLM load testing differs from typical API load testing:
- Requests have **highly variable latency** (short vs long generations) — percentile-based metrics (p50/p95/p99) matter more than averages.
- **Token-based load**, not just request-count load — two identical request rates can have wildly different GPU load depending on prompt/output length, so load tests should vary payload size realistically.
- Test **concurrent streaming connections**, not just request/response — streaming keeps connections open longer and stresses connection-handling differently than simple REST calls.
- Include **tool-calling and RAG-retrieval load** in the test, not just raw LLM throughput, since the bottleneck is often the retriever or a rate-limited external tool, not the model itself.

---

## 25. Multi-Region & Model-Provider Routing

**Missing from the original.**
- **Multi-region deployment** reduces latency for geographically distributed users and provides resilience if one region's provider/infra goes down — but complicates data residency/compliance (Section 27) if user data must stay in-region.
- **Model-provider routing / multi-provider fallback** — route to a secondary provider (e.g., a different hosted model) if the primary is down or rate-limited, avoiding vendor lock-in and giving another layer of the reliability patterns from Section 13 applied at the provider level, not just the model-version level.

---

## 26. Disaster Recovery & Backups

**Missing from the original.**
- **Backup** conversation/vector DB data on a schedule; test restores periodically — an untested backup is not a real backup.
- Define **RTO (Recovery Time Objective)** and **RPO (Recovery Point Objective)** for your AI application, same as any production system — e.g., "if the vector DB is lost, how much re-indexing time / data loss is acceptable?"
- Have a plan for **regenerable vs non-regenerable data**: embeddings can usually be recomputed from source documents (regenerable, lower backup priority) whereas conversation history/user data generally cannot (non-regenerable, higher backup priority) — this distinction should drive your backup investment.

---

## 27. Compliance & Data Governance

**Missing from the original.**
- **Data residency** — some regulations (GDPR, industry-specific rules) require user data to stay within a region; this affects where you can host models/vector DBs and whether you can use a third-party managed model API at all for certain data.
- **Audit logging** — who accessed what data, which tool executed which action, on whose behalf — needed for compliance frameworks like SOC 2, and it's also just good security practice (ties back to Section 14).
- **Right to deletion** — if a user requests data deletion, you need a way to purge their data not just from Postgres but from vector DB entries, cached responses, and traces/logs that might contain their content.

## 28. Production AI Failure Scenarios

Practice explaining these out loud:

| Failure | Response |
|---|---|
| LLM unavailable | Fallback model |
| Vector DB unavailable | Graceful error / fallback retrieval |
| Redis unavailable | Degrade gracefully where possible |
| LLM response too slow | Timeout + fallback |
| Agent infinite loop | Max iterations |
| Huge user prompt | Token limit + validation |
| Malicious document | Indirect prompt injection protection |
| Wrong tool selected | Tool validation + authorization |

## 33. One-Line Interview Answer & Roadmap

> **Production AI is about deploying AI applications reliably at scale while managing latency, cost, security, observability, evaluation, failures, and model quality — using the same production-engineering discipline as any distributed system, extended with GenAI-specific concerns like token economics, prompt/model versioning, and quality regressions that don't show up as infra errors.**
