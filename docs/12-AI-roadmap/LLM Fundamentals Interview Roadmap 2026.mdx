## Phase 1 — What is an LLM?

Start here.

### Understand

```
Text
 ↓
Tokens
 ↓
Neural Network
 ↓
Next-token probabilities
 ↓
Generated tokens
 ↓
Text
```

An LLM fundamentally predicts the next token based on the previous context.

```
"The capital of India is"

Delhi     → 0.94
Mumbai    → 0.02
Kolkata   → 0.01
...

→ Delhi
```

### Interview Questions
- What is an LLM?
- How does an LLM generate text?
- Is an LLM actually "thinking"?
- Why does an LLM sometimes hallucinate?

## Phase 2 — Tokens & Tokenization

Extremely important.

```
"I love React"
       ↓
["I", " love", " React"]
       ↓
Token IDs
       ↓
Neural network
```

### Learn
Token, Token ID, vocabulary, tokenization, subword tokenization (BPE, byte-level BPE), special tokens, input/output tokens.

### Why Developers Care
Tokens affect context window, cost, latency, prompt size, RAG chunk size.

### Interview Question
**Why can 1,000 words sometimes use more than 1,000 tokens?**
> Because tokens aren't equivalent to words; words can split into multiple subword tokens.

## Phase 3 — Embeddings

You already encountered this in RAG — understand the fundamentals here.

```
"React is a JavaScript library"
             ↓
       Embedding Model
             ↓
[0.12, -0.42, 0.81, ...]
```

### Learn
Embedding model, vector, dimensions, semantic similarity, cosine similarity, dense vs sparse representations.

### Important Distinction
> LLM ≠ Embedding model. An LLM generates text. An embedding model converts content into vectors.

### Interview Question
**Why are embeddings important for RAG?**
> Because they allow us to search for content based on semantic similarity, rather than only exact keyword matching.

## Phase 4 — Attention & Transformers

Probably the most important theoretical topic. You don't need to derive every equation, but you must understand the concept.

```
Input
 ↓
Tokenization
 ↓
Embeddings
 ↓
Positional Information
 ↓
Self-Attention
 ↓
Feed Forward Network
 ↓
Transformer Layers
 ↓
Output
```

### Self-Attention
*"Pawan put the laptop on the table because it was heavy."* — what does "it" refer to? Attention helps the model determine relationships between tokens.

### Learn
Query, Key, Value, self-attention, multi-head attention, attention scores, softmax, feed-forward network, transformer block.

### Positional Encoding 🆕
The core attention formula has no inherent sense of token order — position must be injected separately. Know that **RoPE (Rotary Positional Embeddings)** is the current standard in most open-weight models (Llama, Qwen, etc.), and that positional-encoding choice directly affects how well a model extrapolates to longer contexts than it was trained on.

### Core Formula
```
Attention(Q, K, V) = softmax(QKᵀ / √dₖ) V
```
You don't necessarily need to derive it in a software-engineering interview.

### Interview Questions
- What is self-attention?
- Why do we need Q, K, and V?
- Why multi-head attention instead of one large attention operation?
- Why Transformers instead of RNNs?
- Why does positional encoding matter, and what does RoPE do differently from older absolute position embeddings? 🆕

## Phase 5 — Context Window

Very important for real-world AI applications.

```
┌─────────────────────────────┐
│ System prompt               │
│ Conversation                │
│ Retrieved documents         │
│ User question               │
│                             │
│ Context Window              │
└─────────────────────────────┘
```

### Learn
Context window, input tokens, output tokens, context limits, long-context models, context dilution ("lost in the middle" — relevant info in the middle of a long context is often used less reliably than info at the start/end). 🆕

### Interview Question
**Why not simply put the entire company knowledge base into the context?**
> Because of context limits, cost, latency, irrelevant information, and reduced retrieval precision. That's one reason RAG exists.

### Interview Questions (additional)
- What is "lost in the middle," and why does it matter when designing prompts with long context? 🆕

## Phase 6 — Inference & Text Generation

Understand what happens when you call `response = model.generate(...)`.

```
Prompt
 ↓
Model
 ↓
Logits
 ↓
Probabilities
 ↓
Token selection
 ↓
Next token
 ↓
Repeat
```

### Learn
Logits, softmax, probability distribution, autoregressive generation, decoding, greedy decoding, sampling.

### Prefill vs Decode 🆕
Two distinct phases of inference: **prefill** processes the entire input prompt in parallel (compute-bound), while **decode** generates output tokens one at a time (memory-bandwidth-bound). This split explains why long prompts with short answers behave very differently, performance-wise, from short prompts with long answers — a favorite senior-interview distinction.

### Interview Question
**Why does generation happen one token at a time?**
> Most autoregressive LLMs predict the next token conditioned on the tokens already generated.

### Interview Questions (additional)
- What's the difference between the prefill and decode phases, and why does that distinction matter for latency? 🆕

## Phase 7 — Temperature, Top-K, Top-P

You must know these.

### Temperature
Controls randomness. Lower → more deterministic. Higher → more diverse/random.
- Code generation → low temperature.
- Creative writing → higher temperature.

### Top-K
Only consider the top K probable tokens, then sample.

### Top-P (nucleus sampling)
Choose the smallest group of tokens whose cumulative probability reaches P (e.g., 0.9 = top 90% probability mass).

### Repetition/Frequency Penalty 🆕
Reduces the likelihood of tokens that already appeared, preventing repetitive loops — a practical knob you'll actually tune in production far more often than people expect.

### Interview Question
**Top-K vs Top-P?**
> Top-K uses a fixed number of candidates; Top-P dynamically selects candidates based on cumulative probability.

## Phase 8 — KV Cache

A great senior interview topic.

During generation, the model repeatedly needs attention information from previous tokens. Instead of recomputing everything, inference systems cache previously computed Keys and Values.

```
Without KV Cache          With KV Cache
Token 1 → calculate       Token 1 → calculate + cache
Token 2 → recalculate     Token 2 → reuse cache
Token 3 → recalculate     Token 3 → reuse cache
```

### Why It Matters
KV caching improves generation latency and throughput, but increases memory usage.

### Prompt/Context Caching 🆕
A related but distinct production optimization: caching the KV state of a *repeated prefix* (e.g., a long system prompt reused across many requests) so it isn't recomputed per request — this is what API providers mean by "prompt caching," and it directly cuts both cost and time-to-first-token.

### Interview Question
**Why does a larger context window require more GPU memory?**
> Because attention and KV-cache memory grow with the amount of context.

### Interview Questions (additional)
- What is prompt/context caching, and how is it different from the per-request KV cache? 🆕

## Phase 9 — Model Architecture & Sizes

Understand the difference between 7B, 8B, 14B, 32B, 70B — these approximately refer to parameter counts. **Bigger isn't automatically better.**

|---|---|
| Faster | Slower |

## Phase 11 — Instruction Tuning & Alignment

A base model isn't necessarily a good chatbot.

```
Base Model
     ↓
SFT
     ↓
Instruction-following Model
     ↓
Preference/Alignment Training
     ↓
Chat Assistant
```

### Learn
- SFT (Supervised Fine-Tuning)
- RLHF (Reinforcement Learning from Human Feedback)
- DPO (Direct Preference Optimization) — a simpler alternative to RLHF that skips the separate reward model.
- Preference optimization, alignment.
- RLAIF (RL from AI Feedback) 🆕 — using a model instead of humans to generate preference labels at scale; worth knowing as the trend driving cheaper alignment pipelines.

You don't need deep RL mathematics for most AI Engineer interviews — know *what problem each stage solves*, not the derivations.

### Interview Questions (additional)
- At a conceptual level, why is DPO considered simpler than classic RLHF? 🆕

## Phase 13 — Quantization

Important for local LLM deployment.

Suppose a model normally uses FP16 — you can quantize it to 8-bit or 4-bit.

```
Lower precision → Less memory → Faster/cheaper inference → Potential quality loss
```

### Learn
FP32, FP16, BF16, INT8, INT4, GPTQ, AWQ, GGUF.

For your Ollama/local-model work, understanding **GGUF + quantization** is particularly useful — know roughly what Q4_K_M vs Q8_0 naming means (bit-width + quantization method variant) since it appears constantly in Ollama model tags. 🆕

### Interview Questions (additional)
- What do the Q4/Q5/Q8 suffixes in a GGUF model name actually tell you? 🆕

## Phase 14 — Model Selection & Deployment

Where fundamentals become engineering. When choosing a model, consider:

1. **Quality** — does it solve the task?
2. **Context window** — can it handle your input?
3. **Latency** — how quickly does it respond?
4. **Cost** — API cost or infrastructure cost.
5. **Hardware** — can your machine/GPU run it?
6. **Tool calling** — does it reliably support structured tool calls?
7. **Reasoning/coding ability** — important depending on the application.
8. **Open weight vs closed API** 🆕 — data privacy, fine-tuning rights, and vendor lock-in trade-offs, not just raw benchmark scores.

## Phase 15 — Reasoning Models & Test-Time Compute 🆕

By far the biggest gap in most 2025-era roadmaps — reasoning models are now a default interview topic.

### Learn
- **Test-time compute** — spending more inference-time computation (extra reasoning steps) instead of only scaling model size, to improve answer quality on hard problems.
- **Chain-of-thought (CoT)** — prompting or training a model to produce intermediate reasoning steps before a final answer.
- **"Thinking" / reasoning tokens** — models that generate an internal reasoning trace before responding (the modern o1/o3-style and equivalent open-weight reasoning models), and the trade-off of extra latency and cost for better accuracy on multi-step problems.
- When reasoning models help (math, multi-step logic, code debugging) vs when they're overkill (simple lookups, classification) — reasoning tokens cost real money and latency for no benefit on easy tasks.
- Distillation 🆕 — training a smaller "student" model to mimic a larger "teacher" model's outputs (including reasoning traces), a common way reasoning capability gets pushed into smaller, cheaper models.

### Interview Questions
- What is test-time compute, and how is it different from just making the base model bigger?
- When would you *not* want to use a reasoning model, even if it's available?
- What is distillation, and why does it matter for deploying reasoning capability cheaply?

## Phase 16 — Inference Serving at Scale 🆕

Engineering-facing companion to Phase 8's KV cache discussion.

### Learn
- **Continuous batching** — dynamically adding/removing requests from a running batch instead of waiting for a fixed batch to complete, dramatically improving GPU utilization for concurrent users.
- **Speculative decoding** — using a small "draft" model to propose several tokens ahead, which the larger model verifies in parallel, speeding up generation without changing output quality.
- Serving frameworks to recognize by name: **vLLM**, **TGI (Text Generation Inference)**, **llama.cpp** (the engine behind Ollama), **SGLang**.
- Throughput vs latency trade-offs: batching improves throughput (more users served) but can increase per-user latency.
- Time-to-first-token (TTFT) vs time-per-output-token (TPOT) 🆕 — the two latency metrics that actually matter to end users, and why they're optimized differently (TTFT ≈ prefill speed, TPOT ≈ decode speed).

### Interview Questions
- What is continuous batching, and why does it matter for serving many concurrent users?
- What is speculative decoding, and why doesn't it change output quality?
- What's the difference between optimizing for TTFT vs TPOT, and when does each matter more?

## Phase 17 — Structured/Constrained Decoding 🆕

Directly relevant to your Guardrails and structured-output work — worth knowing at the mechanism level, not just "use Pydantic."

### Learn
- **Constrained/grammar-based decoding** — restricting which tokens the model is even allowed to sample at each step (e.g., via a JSON grammar or regex), guaranteeing valid structure instead of hoping and retrying.
- Difference from prompting for JSON: prompting *asks nicely*; constrained decoding *makes invalid tokens impossible to select*.
- Where this runs: server-side (vLLM/Outlines/llama.cpp grammars) vs client-side validation-and-retry (LangChain output parsers) — know both exist and the reliability/latency trade-off between them.

### Interview Questions
- What's the difference between asking a model to "return JSON" in the prompt vs using constrained/grammar-based decoding?
- Where would you enforce structured output — at the inference server level or with a validate-and-retry loop in your application?

## Phase 18 — MoE & Multimodal Architectures 🆕

### Learn
- **Mixture of Experts (MoE)** — a model with many "expert" sub-networks, where only a subset activate per token, letting total parameter count grow without proportionally increasing compute per token (e.g., Mixtral-style architectures). Know the basic trade-off: more total parameters/knowledge capacity, similar per-token compute cost to a smaller dense model, but higher total memory footprint.
- **Multimodal LLMs** — models that accept image (and sometimes audio/video) input alongside text, typically via a vision encoder feeding into the same transformer backbone.
- Why MoE and multimodal are both "bigger capability without proportionally bigger cost" strategies, just along different axes (sparsity vs modality).

### Interview Questions
- What is Mixture of Experts, and why doesn't a bigger MoE model cost proportionally more to run per token?
- At a high level, how does a multimodal LLM process an image alongside text?

## Phase 19 — Evaluation Benchmarks & Safety 🆕

### Learn
- Common benchmarks worth recognizing by name: **MMLU** (broad knowledge), **HumanEval/MBPP** (code), **GSM8K/MATH** (math reasoning), **HellaSwag** (commonsense) — you don't need scores memorized, just to recognize what each measures and their limitations (benchmark contamination, saturation).
- Why benchmark leaderboard rank ≠ "best model for my task" — task-specific evaluation on your own data matters more.
- Safety/alignment evaluation basics — red-teaming, refusal-rate testing — as the model-level counterpart to the application-level guardrails covered in the Guardrails roadmap.

### Interview Questions
- Why can a model that tops a public leaderboard still perform worse than a smaller model on your specific task?
- What does it mean for a benchmark to be "contaminated," and why does that undermine trust in leaderboard rankings?

## Important LLM Concepts You Should Also Know

### Hallucination
LLM generates plausible but unsupported information.

```
LLM knowledge + Prompt + Retrieved context → Generated answer
```

RAG and guardrails help reduce this.

### Temperature vs Hallucination
Don't say: *"Low temperature prevents hallucinations."*
Better: *"Lower temperature makes generation more deterministic, but it does not guarantee factual correctness."*

### Stateless LLM
LLMs generally don't automatically remember previous API calls. Your application provides conversation history:

```
Request 1 → Store messages
Request 2 → Previous messages + new message → LLM
```

This connects directly to your thread memory / cross-thread memory work (see the LangGraph roadmap).

## Quick-Reference Cheat Sheet 🆕

**One-line answers for whiteboard/verbal rounds:**

- **LLM** = a model that predicts the next token given prior context, applied autoregressively to generate text.
- **Tokenization** = splitting text into subword units; token count ≠ word count, and it directly drives cost/latency/context usage.
- **Self-attention** = each token computes a weighted view of every other token (via Q/K/V) to resolve context-dependent meaning.
- **RoPE** = injects positional information by rotating query/key vectors, the current standard for good long-context extrapolation.
- **KV cache** = reuses previously computed attention Keys/Values so each new token doesn't require recomputing the whole sequence.
- **Prefill vs decode** = prefill processes the prompt in parallel (compute-bound); decode generates tokens one at a time (memory-bound).
- **Temperature/Top-K/Top-P** = three different knobs for shaping how "risky" token sampling is; they're not interchangeable and are often combined.
- **Quantization** = trading numeric precision for memory/speed — GGUF + Q4/Q5/Q8 are the practical vocabulary for local Ollama deployment.
- **Test-time compute / reasoning models** = spend more inference-time computation (explicit reasoning steps) to improve accuracy on hard problems, at the cost of latency and token spend.
- **Continuous batching + speculative decoding** = the two biggest levers production inference servers use to serve many users cheaply and quickly.
