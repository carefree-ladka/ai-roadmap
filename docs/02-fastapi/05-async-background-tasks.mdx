## What Is It?

FastAPI supports both `def` and `async def` endpoints. Async endpoints can
`await` I/O so one worker serves many concurrent requests.

## Why Does It Matter?

AI endpoints wait on the network a lot (LLMs, vector DBs). Async lets you
handle many in-flight requests efficiently — if you never block the loop.

## Sync vs Async Endpoints

```python
@app.get("/sync")
def sync_endpoint():
    result = blocking_call()      # runs in a threadpool worker
    return result

@app.get("/async")
async def async_endpoint():
    result = await async_call()   # yields to the loop while waiting
    return result
```

:::note[How FastAPI runs them]
A plain `def` endpoint is run in an external **threadpool** so it won't block
the event loop. An `async def` endpoint runs **on** the loop — so it must not
call blocking code directly.
:::

## Async HTTP and Database Calls

```python
import httpx

@app.get("/proxy")
async def proxy():
    async with httpx.AsyncClient() as client:
        resp = await client.get("https://httpbin.org/get")
        return resp.json()
```

For databases, use an async driver + async session (see
[Database Integration](./08-database-integration.mdx)).

## The Blocking Trap

Never call blocking code inside an `async def` handler:

```python
import time, asyncio

@app.get("/bad")
async def bad():
    time.sleep(5)                 # ❌ freezes the whole loop

@app.get("/good")
async def good():
    await asyncio.sleep(5)        # ✅ non-blocking
```

If you must call a blocking library from async code, offload it:

```python
import asyncio

@app.get("/cpu")
async def cpu():
    result = await asyncio.to_thread(expensive_sync_function, 10_000_000)
    return {"result": result}
```

## Background Tasks

Return the response immediately and do follow-up work afterwards:

```python
from fastapi import BackgroundTasks

def write_log(message: str):
    with open("audit.log", "a") as f:
        f.write(message + "\n")

@app.post("/notify")
async def notify(email: str, tasks: BackgroundTasks):
    tasks.add_task(write_log, f"notified {email}")
    return {"status": "queued"}   # returns now; log written after
```

Use `BackgroundTasks` for lightweight follow-ups (emails, logging). For heavy or
retryable jobs, use a real task queue (Celery, RQ, Arq).

## Common Mistakes

- Blocking calls inside `async def` (freezes all requests).
- Making everything `async` even when the libraries are sync-only.
- Using `BackgroundTasks` for long CPU jobs (use a worker/queue instead).

## Things to Remember

- `async` + `await` for I/O; offload blocking with `to_thread`.
- Sync endpoints are safe (threadpool) but don't scale like async I/O.
- `BackgroundTasks` = quick post-response work.
